# installing in other agents

Any agent that reads Agent Skills folders can run the pack: copy the ten skill folders into a folder it reads, optionally copy the four agents in its format, and paste a short snippet into its instructions file. Of the other agents, only Codex is tested so far, and only for installing and finding the skills and agents; the agents are optional, since without them each skill does the agent's step in the main session.

## 1. copy the skills

With the [skills CLI](https://github.com/vercel-labs/skills), from your project root:

```sh
npx skills add lokeshrana9999/shipyard --skill '*' --agent codex -y
```

Tested with skills CLI 1.7.0 against a local clone of this repo (`npx skills add <path to clone> ...`): it found all ten skills under `plugins/shipyard-delivery/skills/`, copied each folder whole into `.agents/skills/<skill>/`, and wrote a `skills-lock.json` at the project root. `--agent cursor` and `--agent gemini-cli` wrote to the same `.agents/skills/` folder. Add `-g` for your user folder instead of the project. Fetching by GitHub name was tested on 2026-09-29: `npx skills add lokeshrana9999/shipyard --skill '*' --agent codex -g -y` installed all ten skills into `~/.agents/skills/`. With the four Codex agent files copied into `~/.codex/agents/`, `codex exec` listed the skills and the agents concern-reviewer, review-verifier, live-verifier, and test-designer.

Without the CLI, clone the pack outside your project and copy the folders, keeping each one whole (`SKILL.md` plus `references/`):

```sh
git clone https://github.com/lokeshrana9999/shipyard ~/shipyard
mkdir -p .agents/skills
cp -r ~/shipyard/plugins/shipyard-delivery/skills/* .agents/skills/
```

Commit `.agents/skills/` if your team should share the skills. To update, pull and copy again, or symlink the folders instead of copying.

## 2. copy the agents

| Agent | Skills folder (project, user) | Agent files to copy | Agents folder |
|---|---|---|---|
| Codex | `.agents/skills/`, `~/.agents/skills/` | `platforms/codex/agents/*.toml` | `.codex/agents/` or `~/.codex/agents/` |
| Gemini CLI | `.agents/skills/` or `.gemini/skills/`, `~/.gemini/skills/` | `platforms/gemini/agents/*.md` | `.gemini/agents/` or `~/.gemini/agents/` |
| Cursor | `.agents/skills/` or `.cursor/skills/`, `~/.cursor/skills/` | `agents/*.md` | `.cursor/agents/` (its docs say it also reads `.claude/agents/`; unverified) |
| GitHub Copilot | `.agents/skills/` or `.github/skills/`, `~/.copilot/skills/` | `agents/*.md`, renamed `*.agent.md` (unverified) | `.github/agents/` (VS Code's docs say it also reads `.claude/agents/`; unverified) |
| OpenCode | `.agents/skills/` or `.opencode/skills/`, `~/.config/opencode/skills/` | `agents/*.md` (unverified) | `.opencode/agents/` or `~/.config/opencode/agents/` |
| Claude Code | installed by the plugin | `agents/*.md` | installed by the plugin; or `.claude/agents/` |
| anything else | wherever it reads skills | none | none |

Agent file paths are relative to `plugins/shipyard-delivery/` in the clone, e.g. for Codex: `mkdir -p .codex/agents && cp ~/shipyard/plugins/shipyard-delivery/platforms/codex/agents/*.toml .codex/agents/`. The folders are the ones each tool's own docs list. "Unverified" means the tool may not accept Claude Code's frontmatter as-is; skip the agents if they fail to load. An agent that reads no skill folders can still use a skill if its instructions file points at that `SKILL.md`.

`plugins/shipyard-delivery/agents/` holds the source files in Claude Code's format; `plugins/shipyard-delivery/platforms/` holds the Codex and Gemini CLI copies, generated by `node scripts/gen-agents.mjs`. What each agent does is in [agents.md](helper-agents.md).

## 3. paste the AGENTS.md snippet

Add this to the project's `AGENTS.md` (`GEMINI.md` for Gemini CLI) so the agent knows the stage order without loading every skill, and leaves the three user-started skills alone.

```markdown
## Delivery workflow

The ship skill says where the current work stands and which stage comes next.
Work moves through these stages: explain (walkthrough), plan (plan mode or a plan in chat),
test design (design-tests), implement (prisma-workflow when the database schema changes),
verify live (live-verify), review (pr-review: map and review per slice, validate), describe (pr-description),
demo (not built yet). Each stage skill ends with a `next:` line naming the following stage;
flow-diagram (diagrams, used by describe) and skill-auditor are cross-cutting and have none.
Project settings for a skill live in `.claude/shipyard/<skill>.md`, whatever the agent.
Start pr-review, pr-description, and build-workflow only when the user asks for them.
Agents: test-designer, live-verifier, concern-reviewer, review-verifier.
```

## running a skill

Ask for it by name ("run the ship skill"); Codex also takes `$ship` and Cursor `/ship`. Give arguments in the same request: "run the ship skill for all remaining stages", "run pr-review against main". To start one of the helper agents yourself in Codex, ask by name ("spawn the review-verifier agent on these findings").

## what doesn't carry over

- Preloaded skills: a Claude agent's `skills:` list becomes an instruction to read that skill first.
- Nested agents: Gemini agents can't start other agents, and Codex allows one level by default. Agents that would ask a subagent for a decision make it themselves.
- Model: every agent uses the model of the session that starts it; the generated files set no model or reasoning effort, so each tool's default applies.
- Read-only: enforced by the sandbox on Codex; stated in the instructions on Gemini.
- `disable-model-invocation`: Claude Code won't start `pr-review`, `pr-description`, or `build-workflow` unasked. Agents that ignore the field may, so the snippet says not to.
- The `signal` output style, slash-command arguments, and the Workflow tool are Claude Code only. Elsewhere, say a skill's arguments in the request.
- Project settings stay at `.claude/shipyard/<skill>.md` in every agent; the `.claude` in the path doesn't mean Claude Code only.
